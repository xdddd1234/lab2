# ADR-0001: Визначення меж варіантів використання

- **Статус:** Accepted
- **Дата:** 2026-10-21
- **Проєкт:** Library Management System

## Context and Problem Statement

Під час моделювання вимог Library Management System необхідно визначити межі варіантів використання (Use Cases), щоб уникнути дублювання сценаріїв і забезпечити відповідність між EARS-вимогами, User Stories, Gherkin-сценаріями та ER-моделлю лабораторної №1.

Система підтримує перегляд каталогу, реєстрацію читачів, видачу та повернення книг, перегляд історії видач і надсилання нагадувань.

Потрібно вирішити, які дії мають бути окремими Use Cases, а які — обов'язковими або умовними допоміжними сценаріями.

## Decision Drivers

- Кожен основний Use Case повинен представляти зрозумілу ціль актора.
- Сценарії повинні бути однозначними та придатними для тестування.
- Необхідно правильно використовувати UML-зв'язки `<<include>>` і `<<extend>>`.
- Поведінка системи повинна відповідати сутностям `Reader`, `Book`, `Author`, `Category` та `Loan`.
- Потрібно зберегти трасування між вимогами та сценаріями.
- Зовнішній Сервіс сповіщень не повинен вимагати додавання нової сутності до ER-моделі.

## Considered Options

### Варіант 1 — Один загальний Use Case для всіх операцій

Створити один варіант використання «Керування бібліотекою», який включає реєстрацію, пошук, видачу, повернення та нагадування.

**Переваги:**
- Менша кількість елементів діаграми.
- Простіша початкова структура.

**Недоліки:**
- Змішуються різні цілі акторів.
- Складніше визначити передумови та результати.
- Ускладнюється трасування вимог і тестових сценаріїв.
- Втрачається різниця між обов'язковими перевірками та умовними діями.

### Варіант 2 — Окремі основні Use Cases з допоміжними сценаріями

Виділити шість основних Use Cases відповідно до цілей системи.

Використовувати `<<include>>` для обов'язкових перевірок і `<<extend>>` для умовного пошуку.

**Переваги:**
- Чіткі межі сценаріїв.
- Простіше пов'язувати вимоги з Use Cases.
- Зрозуміліша поведінка для читача та бібліотекаря.
- Зручніше розробляти окремі Gherkin-сценарії.
- Відображається взаємодія із зовнішнім сервісом.

**Недоліки:**
- Діаграма містить більше елементів.
- Потрібно підтримувати узгодженість між кількома артефактами.

## Decision Outcome

**Обрано варіант 2:** окремі основні Use Cases з допоміжними сценаріями.

### Видача та повернення книги

UC-03 «Видача книги» та UC-04 «Повернення книги» є окремими варіантами використання.

Видача створює новий запис `Loan`, а повернення завершує наявний запис установленням `return_date`.

Ці операції мають різні цілі, передумови та результати.

Під час видачі застосовується правило BR-01: бібліотекар задає `due_date`, яка не може бути раніше `loan_date`.

### Надсилання нагадування

UC-06 «Надсилання нагадування» є окремим Use Case, оскільки запускається за часовою умовою, а не безпосередньою дією бібліотекаря.

Відповідно до BR-02 система ініціює нагадування о 09:00 за часовим поясом `Europe/Kyiv` у дату `due_date` активної видачі.

Зовнішній Сервіс сповіщень бере участь у виконанні цього сценарію як вторинний актор.

### Використання include

UC-03 «Видача книги» включає перевірку доступності книги через `<<include>>`.

Ця перевірка є обов'язковою, оскільки книга не може мати більше однієї активної видачі.

UC-02 «Реєстрація читача» включає перевірку унікальності email через `<<include>>`.

Ця перевірка необхідна для дотримання обмеження унікальності `Reader.email`.

### Використання extend

«Пошук книги за назвою» розширює UC-01 «Перегляд каталогу» через `<<extend>>`.

Відповідно до BR-03 розширення виконується лише за наявності непорожнього пошукового запиту.

Звичайний перегляд каталогу залишається доступним без пошуку.

## Consequences

### Позитивні наслідки

- Основні Use Cases відповідають окремим цілям акторів.
- Обов'язкові перевірки відокремлені від умовних розширень.
- Збережено узгодженість із ER-моделлю лабораторної №1.
- Спрощено трасування між EARS-вимогами, User Stories та Gherkin-сценаріями.
- Уточнення після AI-аудиту відображені в моделі поведінки.

### Негативні наслідки

- Необхідно підтримувати узгодженість між специфікацією, діаграмою та матрицею трасування.
- Зміна бізнес-правил може вимагати оновлення декількох файлів.
- Інтеграція із зовнішнім Сервісом сповіщень потребує окремих тестів.

## Зв'язок із трасуванням

Основні варіанти використання UC-01–UC-06 пов'язані з вимогами REQ-01–REQ-10 у файлі `traceability.md`.

REQ-09 і REQ-10 представлені через UC-06, але поки не мають окремих Gherkin-сценаріїв. Ця прогалина задокументована для майбутнього інтеграційного тестування.

## Висновок

Розділення сценаріїв за цілями акторів забезпечує зрозумілу UML-модель, полегшує перевірку вимог і підтримує відповідність між поведінкою системи та її моделлю даних.
